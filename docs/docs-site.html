Multitenant Platform
Secure Data Orchestration

A shared platform where technical teams submit zip files for automated processing. Each run provisions infrastructure, validates via Lambda, processes via ECS Fargate, and audits every step in DynamoDB.

AWS S3 · ECR · Lambda ECS Fargate · DynamoDB Terraform IaC GitHub Actions CI/CD Python 3.12
01

System Architecture

The platform follows an event-driven serverless pattern. A GitHub release triggers the full pipeline — from infrastructure provisioning to data processing and audit.

End-to-end system flow
🪣
S3 Upload Bucket
Private, encrypted (AES-256). Receives .zip uploads tagged with organization-id. PutObject events auto-trigger Lambda.
⚡
Lambda Validator
Python 3.12. Reads org-id tag, validates file size (<500MB) and content-type. Writes audit record then fires ECS task.
🐳
ECS Fargate Processor
Containerised Python. Downloads zip from S3, logs contents and metadata, writes COMPLETE audit record to DynamoDB.
📋
DynamoDB Audit Table
PAY_PER_REQUEST. PK: org_id. SK: timestamp#event_type. PITR enabled. Every transition is immutably recorded.

Deployment Guide

One-Time AWS Admin Setup

These steps are performed once per project by the AWS admin. They create the shared foundation all developers rely on.

1
Create S3 Bucket for Terraform State
Create bucket multitenant-platform-terraform-statefiles in us-east-1 with versioning enabled. This stores Terraform state files securely.
2
Create IAM Group and Minimum Permissions
Create group multitenant-platform-company-developers. Attach the least-privilege policy below. All platform users are added to this group.
3
Create ECS Service-Linked Role
IAM → Roles → Create role → AWS service → Elastic Container Service (not Task). Or via CLI:
aws iam create-service-linked-role --aws-service-name ecs.amazonaws.com
4
Provision Developer Users
For each developer: create IAM user → add to the group → generate Access Keys → share credentials securely. Also provide VPC_ID and SUBNET_ID.
⚠️
IAM JSON syntax note: The policy below requires a comma between every Statement object. A missing comma between the ECR and EC2 blocks is a common mistake that will cause a silent parse error in the AWS Console.
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": ["s3:*"],
      "Resource": "arn:aws:s3:::multitenant-platform-*" },
    { "Effect": "Allow", "Action": ["dynamodb:*"],
      "Resource": "arn:aws:dynamodb:*:*:table/multitenant-platform-*" },
    { "Effect": "Allow", "Action": ["lambda:*"],
      "Resource": "arn:aws:lambda:*:*:function:multitenant-platform-*" },
    { "Effect": "Allow", "Action": ["iam:*"],
      "Resource": "arn:aws:iam::*:role/multitenant-platform-*" },
    { "Effect": "Allow", "Action": ["logs:*"],
      "Resource": "arn:aws:logs:*:*:*" },
    { "Effect": "Allow", "Action": ["ecs:*"],  "Resource": "*" },
    { "Effect": "Allow", "Action": ["ecr:*"],  "Resource": "*" },
    { "Effect": "Allow",
      "Action": ["ec2:CreateSecurityGroup","ec2:DeleteSecurityGroup",
                 "ec2:AuthorizeSecurityGroupEgress","ec2:RevokeSecurityGroupEgress",
                 "ec2:DescribeSecurityGroups","ec2:DescribeSecurityGroupRules"],
      "Resource": "*" }
  ]
}

GitHub Repository Secrets

Each developer must set the following secrets in their fork at Settings → Secrets and variables → Actions:

SecretSourcePurpose
AWS_ACCESS_KEY_IDFrom adminAuthenticate GitHub Actions runner to AWS
AWS_SECRET_ACCESS_KEYFrom adminAuthenticate GitHub Actions runner to AWS
AWS_DEFAULT_REGIONFrom adminTarget AWS region (e.g. us-east-1)
VPC_IDFrom adminVPC for ECS Fargate security group
SUBNET_IDFrom adminSubnet for Fargate task networking
STATEFILE_BUCKET_NAMEAdmin or defaultS3 bucket holding Terraform state
STATEFILE_BUCKET_REGIONAdmin or defaultRegion of the Terraform state bucket
ℹ️
Terraform backend note: Terraform S3 backend blocks do not support variable interpolation. The bucket and region values must be injected at terraform init time via -backend-config flags, which the pipeline handles automatically using the secrets above.

Terraform Variable Defaults

Edit infra/environments/dev/terraform.tfvars to set your VPC and subnet before the first run:

aws_region   = "us-east-1"
project_name = "multitenant-platform"
environment  = "dev"
vpc_id       = "vpc-xxxxxxxxxxxxxxx"   # your default VPC
subnet_id    = "subnet-xxxxxxxxxxxxxxx" # a public subnet in that VPC

CI/CD Pipeline

The pipeline triggers automatically on every GitHub Release that includes a .zip asset. It runs sequentially through 7 steps.

GitHub Actions pipeline — process_pipeline.yml

How to Trigger the Pipeline

1
Prepare a .zip file
Any valid .zip will work. Create a test file: echo "hello" > sample.txt && zip mydata.zip sample.txt
2
Create a GitHub Release
Go to Releases → Draft a new release. Set a tag (e.g. v1.0.0), title, then drag-and-drop your .zip into the assets area. Click Publish release.
3
Monitor the workflow
Go to Actions → Multitenant Platform Pipeline. Each step prints detailed logs including Terraform output names, S3 keys, ECS task IDs, and the final DynamoDB audit trail.

Audit Trail

Query the DynamoDB table after the run completes:

aws dynamodb query \
  --table-name multitenant-platform-dev-audit \
  --key-condition-expression "org_id = :oid" \
  --expression-attribute-values '{":oid":{"S":"<your-github-org>"}}' \
  --output table \
  --query 'Items[*].{Event:event_type.S,Status:status.S,Details:details.S}'

Expected output:

EventStatusDetails
VALIDATEDSUCCESSorg-id=<org>, size=…MB
PROCESSING_STARTSUCCESSECS Fargate task: <task-id>
COMPLETESUCCESSProcessed file.zip, …MB, N files

View ECS Container Logs

aws logs tail /ecs/multitenant-platform-dev-processor --since 10m --format short

Hybrid Backbone Strategy

A Member Organisation may require that their data never leaves their premises. The architecture supports this through three configuration seams — without any code changes to the backbone logic.

Cloud vs On-premises topology

Three Configuration Seams

SeamLayerCloud (default)On-premisesChange required
1 Storage AWS S3 MinIO / Ceph / any S3-compatible Set AWS_ENDPOINT_URL_S3
2 Compute ECS Fargate (ecs:RunTask) Relay Agent polling SQS → Docker / k8s Add Relay Agent (~80 lines Python)
3 Audit DB AWS DynamoDB DynamoDB Local / ScyllaDB Alternator Set AWS_ENDPOINT_URL_DYNAMODB
✅
Key principle: boto3 respects AWS_ENDPOINT_URL_* environment variables natively. The validation logic, audit schema, and container interface are identical in both topologies. Only the transport endpoints differ — expressed as configuration, not code.
05

Security Model

IAM least-privilege boundaries

Encryption at Rest

  • S3 bucket: SSE-S3 (AES-256) applied to all objects
  • DynamoDB table: server-side encryption enabled
  • ECR repository: AES-256 image encryption
  • S3 public access: fully blocked at bucket level

Least-Privilege IAM

  • Lambda role scoped to specific bucket ARN, table ARN, task ARN
  • ECS task role restricted to uploads/* S3 prefix only
  • iam:PassRole conditioned on ecs-tasks.amazonaws.com
  • No wildcards on sensitive resource types

Teardown

All infrastructure can be destroyed from GitHub Actions without any local tooling.

1
Go to Actions → Destroy Infrastructure
Navigate to the Actions tab in the GitHub repository.
2
Run workflow manually
Select Destroy Infrastructure from the workflow list. Click Run workflow → Run workflow. The workflow runs terraform destroy -auto-approve.
3
Manual cleanup (if needed)
The Terraform state S3 bucket and IAM group are not managed by Terraform and must be deleted manually in the AWS Console if no longer needed.
⚠️
S3 force_destroy = true: The upload bucket is configured with force_destroy = true, so terraform destroy will delete all objects inside it without confirmation. Ensure any files you wish to retain are backed up first.

Known Issues & Improvement Scope

🔑
Credential Distribution
AWS access keys are shared via GitHub secrets. A better approach is OIDC federation (aws-actions/configure-aws-credentials with role-to-assume) to eliminate long-lived keys entirely.
🤖
Pipeline Automation
Trigger the pipeline automatically when a file is uploaded to Google Drive or an S3-compatible store using n8n or a custom webhook, removing the need for a manual GitHub Release.
📦
Multi-environment
Currently only a dev environment exists. Add staging and prod directories under infra/environments/ with separate state keys and variable files.
🔔
Failure Alerting
DynamoDB records FAILED events but there is no active notification. Consider an EventBridge rule on DynamoDB Streams to trigger an SNS alert on any status=FAILED record.
